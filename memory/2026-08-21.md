## Nearby map gray basemap — Redis cleared as NOT culprit; tile-cache fix
- **Q:** "redis run vai rako cha? Nearby map load vako xaina." → Verified: **Redis IS running** (127.0.0.1:6379 LISTENING, app ESTABLISHED). Backend `/api/v1/places/all` 200, `tile.openstreetmap.org` 200 with multiple UAs, `a.basemaps.cartocdn.com` 200. Server-side fine.
- **Real issue:** default (non-satellite) OSM layer showed **gray/blank tiles** while satellite worked, everything else (markers, API) fine. This matches the offline SQLite `tile_cache` serving a corrupt/empty/once-failed blob forever (tiles never expired). OfflineTileProvider returns `TileProvider.transparentImage` (gray) on any failure and only persisted valid 200 blobs, but a previously-persisted bad blob was served indefinitely.
- **Fixes (Flutter):**
  1. `offline_db_service.dart getCachedTile()` — now rejects+deletes empty/corrupt `blob_data`, returns `null` on overlong-stale (`maxAgeMs` param). Added `clearTile(z,x,y,tileType)`.
  2. `offline_tile_provider.dart` — `OfflineTileProvider.tileCacheStaleAfterMs = 90d` const; `_isPlausibleImage()` (PNG `89 50 4E 47` / JPEG `FF D8 FF` signature check). `_CachedTileImage._load` only uses cached tile if plausible+not stale, try/catch decode → on failure `clearTile` + re-download.
  3. `nearby_map_screen.dart` default (standard) TileLayer — added Carto fallback `https://a.basemaps.cartocdn.com/light_all/{z}/{x}/{y}.png` so OSM rate-limit/block still renders real tiles.
- **Verified:** `flutter analyze` on the 3 touched files — 0 errors; only pre-existing unused-import warnings in the two service files (out of scope, left). NOTE: user on emulator/device must rebuild app for the purge logic to run (no DB migration needed — `cached_at` column already existed).

## Admin Live Map HTTP 500 — ROOT CAUSED + FIXED
- **Symptom:** `/admin/live-map` returned "HTTP ERROR 500" (localhost unable to handle).
- **Root cause:** `AdminController::liveMap()` ran `Place::with('category','images')->get()` over the
  full active-POI set (77,319 places after OSM import), then json-encoded it into the blade.
  PHP `memory_limit` is 128M → "Allowed memory size ... exhausted" → Laravel 500.
  This regressed once the OSM import grew the `places` table past ~the 128M threshold (it 200'd
  earlier with fewer rows). No code bug in the blade/route; the route `/live-map` → `liveMap` was fine.
- **Fix (backend/app/Http/Controllers/AdminController.php `liveMap()`):**
  1. `@ini_set('memory_limit', '512M')` — headroom for the one aggregation endpoint.
  2. Replaced eager `with('category','images')` with a lean `select()` + `leftJoin`
     `place_categories` (only map-needed columns; categories have NO `color` column → keep
     `'#6366f1'` fallback — don't resurrect `c.color`).
  3. First image per place now via a light `PlaceImage::query()->orderBy('id')->get(['place_id','image_url'])`
     loop instead of eager-loading every image model. Only 2 image rows currently.
  - ⚠️ This framework's Eloquent/Query Builder has **NO `chunk()` / `chunkById()`** (verified via
    grep on both Builder.php files) — do NOT call them; they'd `BadMethodCallException` → 500.
- **Verified:** real Laravel boot harness invoked `liveMap()` → `view=admin.live_map`, counts
  places=77319 reports=3 alerts=0, peak 344MB (was >128M OOM). `php -l` clean.
- **Note/scale:** peak ~344MB grows with place count; revisit (server-side clustering / bounding the
  marker set, e.g. keep latest N) before the table grows much past ~100k.
