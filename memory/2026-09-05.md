## SOS — "Network error please Try Again" investigation (same date)

User reported console message "Network error please Try Again" (sos_provider line ~204 generic catch in `activateSos`).

Findings:
- **Backend healthy**: `http://127.0.0.1:8000/api/v1/sos/nearby` AND `http://192.168.10.67:8000/...` both return 200. Migrations ran, users table has `avatar`+`phone` (needed by `forMe`). No code bug server-side.
- **Root cause**: generic catch in `activateSos` only matched SocketException/"Connection refused"/422/429/500 strings; anything else (esp. **timeout**, or a DioException whose `.toString()` didn't contain those) fell through to the misleading "Network error. Please try again." Real device + stale/unreachable dev host (default `devPhone=192.168.10.67`) → timeout → generic message.
- **Fix**: added `SosProvider._friendlyError(Object e, String fallback)` — inspects `DioException` type (timeout/send/receive → "Connection timed out. Make sure your phone and the server are on the same network...", connectionError→cannot reach, badCertificate, badResponse with statusCode 401/403/429/500→specific msg), plus string fallback for SocketException/host lookup. Applied to `activateSos`, `resolveSos`, `cancelSos`.
- `flutter analyze` sos_provider + emergency: 0 errors / 0 warnings (57 infos = withOpacity + prefer_final_fields). Removed `case DioExceptionType.unknown:` to avoid unreachable_switch_default warning.

## SOS — root cause FOUND: type-cast crash (same date) ✅

User then pasted a **success** server response for an already-active SOS (`duration_seconds: 5349.225766`, i.e. a float) followed by the app still printing a network error.

**Actual root cause**: server `formatSos()/formatNearbySos()/forMe` compute `duration_seconds` via Carbon `diffInSeconds()` → returns a **float** (e.g. `5349.225766`, `10.88`, etc.) and lat/lng/accuracy as numeric/string. But Flutter `SosAlert.fromJson` assigned `durationSeconds: json['duration_seconds']` directly to `int?` → **`type 'double' is not a subtype of type 'int?'` TypeError**. That threw *inside* the `success == true` branch of `activateSos`, got caught by the generic catch → falsely reported "Network error. Please try again." Server worked fine the whole time.

**Fixes**:
- Flutter `SosProvider`: added `int? parseInt(dynamic)` (int→itself, num→round, String→tryParse, null→null) and used it for `durationSeconds` + `contactsNotified`. Now float `duration_seconds` parses safely. `flutter analyze` on sos_provider + emergency: 0 errors/0 warnings (45 info = withOpacity + prefer_final_fields).
- Backend `SosController`: cast duration to `(int)` at all 3 produce sites (forMe line ~117, show line ~320, formatNearbySos line ~420) so API returns clean ints. `php -l` clean, `route:list` OK.

Lesson: never assign an unchecked JSON number to an `int?` in Dart; always round/parse. This same pattern could bite other models — keep an eye on `double` fields from Carbon `diffInSeconds`.
